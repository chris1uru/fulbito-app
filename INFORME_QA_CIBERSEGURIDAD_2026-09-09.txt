======================================================================
1. RESUMEN EJECUTIVO
======================================================================

Estado general: NO APTO PARA APROBAR UNA LIBERACION SIN EXCEPCIONES.

Motivos principales:

- El API activo usa HTTP sin cifrado. Credenciales, bearer tokens y datos pueden ser
  interceptados o modificados por un atacante en la red.
- El lint falla con 11 errores y 2 advertencias.
- npm audit informa 4 entradas vulnerables: 3 moderadas y 1 alta upstream.
- No hay pruebas unitarias, de componentes, integracion ni E2E. Cobertura automatizada
  aparente: 0%.
- No se pudo validar la autorizacion real entre PLAYER, OWNER y ADMIN ni ejecutar los
  flujos completos de negocio porque no se proporcionaron cuentas de prueba ni un
  entorno desechable.
- Se identificaron defectos estaticos de autorizacion de rutas, carreras de requests,
  manejo de fechas, validacion y recuperacion de errores.

Aspectos positivos:

- Los bundles de Android, iOS y web se generan correctamente.
- expo-doctor completa 21/21 controles.
- Las lecturas publicas del API respondieron y sus esquemas basicos fueron coherentes.
- Se probaron 53 de las 54 operaciones API inventariadas de forma no destructiva.
- Las 30 solicitudes mutantes probadas sin autenticacion fueron rechazadas con 401.
- CORS rechazo un origen hostil.
- No se encontraron secretos versionados como API keys, JWT, claves privadas o tokens.
- El token se guarda en SecureStore en Android/iOS y en sessionStorage en web.
- No se observaron eval, WebView, HTML inseguro ni logs de contrasenas o tokens.

Conteo de hallazgos registrados en este informe:

- Criticos: 0 confirmados.
- Altos: 3.
- Medios: 12.
- Bajos: 13.
- Riesgos que requieren backend/cuentas para confirmarse: 5.

La compilacion exitosa demuestra que el codigo puede empaquetarse; no demuestra que
todos los botones, permisos, navegacion, reglas de rol y operaciones autenticadas
funcionen correctamente en dispositivos reales.

7. HALLAZGOS PRIORIZADOS
======================================================================

ALTO-01 - API y credenciales transmitidos por HTTP

Evidencia:
- .env:1 y .env.example:1 usan http://.
- src/services/api.js:28-35 envia JSON y Authorization al host configurado.
- Login, registro y cambio de contrasena usan el mismo transporte.
- La prueba dinamica confirmo que el servicio HTTP esta activo y HTTPS no negocia.

Impacto:
Intercepcion o alteracion de contrasenas, tokens bearer, datos personales, reservas y
firmas de subida por un atacante en la misma red o en posicion MITM.

ALTO-02 - Ruta Buscar Rival accesible por URL a roles no PLAYER

Evidencia:
- app/(tabs)/_layout.jsx:52-60 oculta la tab para otros roles.
- app/_layout.jsx:34-39 permite el grupo tabs a cualquier autenticado.
- app/(tabs)/buscar-rival.jsx no valida rol.

Impacto:
OWNER o ADMIN puede abrir la ruta por deep link/web. La severidad servidor depende de
que el backend valide correctamente el rol.

ALTO-03 - OWNER puede abrir alta de complejo y solicitar /undefined

Evidencia:
- app/_layout.jsx:40-48 protege venueForm para OWNER y ADMIN.
- VenueManagementScreen.jsx:148-160 solo muestra Crear a ADMIN.
- VenueFormScreen.jsx:192-201 hace update para no-ADMIN aunque mode=create y venueId
  puede no existir.

Impacto:
Flujo roto por deep link y solicitud PUT /api/owner/venues/undefined. Si el backend
tuviera validaciones insuficientes, amplia superficie de autorizacion.

MEDIO-01 - No existe suite automatizada

Impacto:
No hay deteccion automatica de regresiones en reservas, roles, pagos, cancelaciones,
fechas, imagenes o matchmaking.

MEDIO-02 - El lint falla

Impacto:
El pipeline definido no puede quedar verde con el estado evaluado. Los errores son
principalmente de formato, pero las advertencias revelan logica/imports no usados.

MEDIO-03 - DoS en cadena de Expo Router

Evidencia:
- expo-router 57.0.20 -> query-string 7.1.3 -> decode-uri-component 0.2.2.
- GHSA-vcc3-ghjq-m6fr.
- app.json registra el esquema de deep link fulbito.

Impacto:
Un enlace con porcentajes malformados podria consumir CPU y bloquear app/pestana.

MEDIO-04 - Parametros ausentes causan 500 en disponibilidad

Evidencia dinamica:

8. RIESGOS NO CONFIRMADOS QUE EXIGEN BACKEND Y CUENTAS
======================================================================

RIESGO-01 - IDOR/BOLA

Se deben cruzar IDs de reservas, sedes, canchas, horarios, bloqueos, imagenes e
intereses entre dos PLAYER y dos OWNER. El cliente permite construir requests por ID;
solo el servidor puede impedir acceso a objetos ajenos.

RIESGO-02 - Escalamiento vertical

Hay que intentar cada endpoint OWNER/ADMIN con PLAYER, cada recurso de OWNER B con
OWNER A y toda accion administrativa con OWNER.

RIESGO-03 - Token web en sessionStorage

Una futura XSS o dependencia comprometida podria leerlo. No se encontro un sink XSS
directo en esta auditoria. Para web, una cookie HttpOnly/Secure/SameSite reduce riesgo.

RIESGO-04 - Destino Cloudinary confiado desde backend

cloudinary.js usa uploadUrl recibido del servidor sin validar esquema/host. Un backend
comprometido o MITM en HTTP podria redirigir la imagen y parametros firmados.

RIESGO-05 - Autorizacion/RLS no verificables

No hay backend ni SQL en este repositorio. Las rutas protegidas de Expo Router son UX,
no una barrera de seguridad. El servidor debe validar rol, propiedad y tenant en cada
operacion.

======================================================================
9. MATRIZ MINIMA PENDIENTE PARA CERTIFICAR LA APP
======================================================================

Prioridad P0:

- Login exitoso/fallido, expiracion, logout y revocacion para los tres roles.
- Acceso directo/deep link a cada ruta con anonimo, PLAYER, OWNER y ADMIN.
- Intentos IDOR con dos jugadores y dos propietarios.
- Reserva concurrente del mismo turno desde dos sesiones.
- Cancelacion PLAYER dentro/fuera de plazo y cancelacion OWNER.
- Marcar pago, doble pulsacion e idempotencia.
- Alta/edicion/desactivacion de OWNER, complejo y cancha en staging.
- Confirmar que ninguna credencial/token viaje por HTTP.

Prioridad P1:

- Agenda dia/mes y combinacion de todos los filtros.
- Reserva manual: fecha invalida, cancha ajena, turno ocupado y errores transitorios.
- Matchmaking: publicar, interes repetido, privacidad, cerrar y carrera de requests.
- Horarios solapados, cruce de medianoche y bloqueos sobre reservas existentes.
- Subida multiple/parcial, limites, portada, borrado y Cloudinary host validation.
- Fechas en America/Montevideo desde dispositivos en otras zonas.
- Android e iOS reales: galeria, mapas, Waze, llamada, WhatsApp y deep links.

Prioridad P2:

- VoiceOver/TalkBack, foco modal, contraste, escalado de texto y tamanos tactiles.
- Paridad funcional web/nativo.
- Red lenta, offline, timeout, JSON invalido, 401 y 500 en cada pantalla.
- Performance con volumen alto de complejos, reservas, imagenes y solicitudes.
- Rate limiting controlado para login y endpoints costosos.

Datos necesarios para ejecutar esta matriz:

- URL HTTPS de staging.
- Dos cuentas PLAYER, dos OWNER y un ADMIN.
- Sedes/canchas/reservas desechables y permiso para crear/eliminar.
- Dispositivo o emulador Android y simulador/dispositivo iOS.
- Definicion esperada de paridad web y politica de publicacion de telefonos/ubicacion.

======================================================================
10. CRITERIO DE SALIDA RECOMENDADO
======================================================================

No liberar hasta cumplir como minimo:

- API HTTPS obligatorio en todos los ambientes usados con credenciales reales.
- Lint en verde.
- Dependencias vulnerables evaluadas/actualizadas sin romper la matriz Expo.
- Autorizacion por rol y por propiedad probada negativamente en backend.
- Sin defectos P0/altos abiertos.
- Tests automatizados para autenticacion, rutas por rol, reservas, cancelacion, pago,
  concurrencia y fechas.
- Smoke E2E en Android, iOS y web.
- Evidencia de que logs y respuestas servidor no exponen tokens, stack traces ni PII.

Evaluacion final:

La app esta en un punto funcionalmente empaquetable y el API publico responde, pero no
esta certificada de extremo a extremo. La ausencia de cifrado en el API, el lint roto,
las dependencias reportadas y la falta total de tests/autorizacion autenticada impiden
considerarla lista para produccion con un nivel de confianza QA y seguridad adecuado.
